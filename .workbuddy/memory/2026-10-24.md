## 1.18.2 第一份现场日志的结论

用户给的 `obmind-trace-20261024-081420.log`（210 行，252 节点，`C0_ MOCs/AI Agent-MOC.md`）。

### 日志坐实的两件事

1. **每次刷新都在全量 setData**：`refresh.plan kind=structure` 反复出现（约 4 秒一次），
   而 `guard.strip n=2/3/3/10` 说明一轮重建只影响 2–10 个节点 —— 为了几个节点重建整张
   252 节点的图。`rebuild.start` → `rebuild.ghost` 之间 **400–550ms**，
   且这期间 frame 号只走 1 帧 = 主线程被占死。
2. **fadeGuard 窗口开错了时刻**（真 bug）：`fadeGuardUntil` 是 setData **之前**

### 改动
- `fadeGuardUntil` 在 `await mm.setData()` **之后**重设 `now + 120`（原来是调用前 +50）。
  120ms 够 d3 跑完 duration 0 的收尾，又短到不误伤手点的折叠淡出。
- `app/plan.ts` 的 `Projection` 加 `reason`（force/noSrc/multi/children/line/depth/blockOnly）
  与 `at`（行号）；新导出 `explainDiff(prev, next, limit)` 打具体差异
  （`.0.0 line 192->193 "123"` 这种）。`tmp/diffProbe.ts` 验证三种输入。
- 日志新增 `rebuild.setData dt`、`rebuild.ghostItem`（被换掉的前 3 个节点名）、
  `refresh.diff`、`rebuild.start nodes`、`refresh.plan lines/nodes`。

### 待确认（下一份日志）
`why=line` 的概率最大（在节点之间插空行 → 后面所有行号 +1 → 判成结构变化）。

真要修得先把「按结构序把新行号写回 DOM」补上。

## 1.18.4 拖动整块走（XMind 式）

用户：「新增和拖动节点，拖动的时候可以先把线去掉，拖动部分是一个整体，这样只用建立一根线」。

### 根因
markmap 的节点 g 是**扁平**的（`this.g.selectAll().data()` 一起挂在同一个父容器里），
父子关系只体现在 `data-path` 与 transform 上。所以只改拖动根的 transform 时，
整棵子树的卡片留在原地，而自绘连线（绝对坐标、画在子节点 g 里）跟着父/子各自
不同的位移被拉成一片长条 —— 就是用户说的「飘线」。

### 做法
- 按下时按 path 前缀收集整棵子树（`p === r || p.startsWith(r + ".")`），
  多选组再并上 `groupOf()` 给出的其它顶层成员。
- 拖动时给每个成员 g 写 **CSS `translate`**（不是 transform 属性）：
  它与 markmap 写的 `transform` 是**叠加**关系，markmap 不会覆盖，观察器也不会被唤醒
  （style 分支只认 foreignObject）。px 在 SVG 元素上是**用户单位**，
  所以要 `dx / k`（k = `svg.__zoom.k`）。
- 整块平移后块内线天然还是对的（线自身随子 g 平移同量，父子同步）；
  只有「原父 → 块根」那一根会歪 → 直接 `display:none` 摘掉。这就是「只用一根线」。
- 遮挡：SVG 没有 z-index。拖动开始时把成员的 g 依次 `parent.appendChild` 到末尾
  = 提到最上层（相对顺序不变）。代价是观察器看到一批 childList → 补一次全量绘制（一次，可忽略）。
- 松手：`onDrop` 改成返回 `boolean`（是否真的发出写入）。true → 位移保持不动，
  rAF 轮询 `isConnected` 等 setData 把这批 g 换掉（900ms 兜底）；false → 当场弹回。
  否则会先弹回原位再跳到新位置。
- 预览线做过又删了：落点卡片永远在鼠标下，与块根卡片重叠 → 线长为 0 永远不显示。
  落点提示（描边框 / 插入横线）本来就说清楚了。

### 坑
- `data-path` **属性不存在**（markmap 没写），必须读 `__data__.state.path`，
  值形如 `"1.2.3"`（state.id 序列，根是 `"1"`）。
- 用 `display:""` 恢复被 CSS `display:none` 隐藏的元素是无效的（样式表会重新生效）——
  要么 CSS 不写 none，要么恢复时写具体值。
- Escape / pointercancel 走 `reset(false)`，必须在这里把摘掉的那根线还原，
  否则取消一次拖动之后它永久消失。

### 验证
`tmp/panProbe.ts`（前提）：CSS translate 与 transform 叠加 ✓、屏幕位移 = k×用户位移 ✓、
块内连线与卡片间距 0.0 ✓。`tmp/dragProbe.ts`（交互，Playwright 真鼠标）：
整块位移 = 鼠标位移、块内一致 spread=0、外部线隐藏、松手还原、onDrop 收到 (src,target,mode)。
截图 `tmp/dragProbe-mid.png` 确认块被提到最上层后不再被目标卡片盖住。

## 1.18.5 review 1.18.4：两个自作自受的 bug

用户报「新建节点已有内容，点开编辑却显示『新节点』，失焦又恢复」+「飘线还在」。

### Bug 1（1.18.4 之前就有，这次才显形）：patch 通道从不回写 `payload.src`

编辑框的初始文本走 `editorValueOf(src)` → `src.text`，而 `src` 来自 DOM 的
`__data__.payload.src`。`applyPatch` 只改了 `data.content` 和 `innerHTML`，
**payload.src 一直是旧的**。新建节点后第一次改字必然踩到（旧值是占位文案「新节点」）：

```
新建 → 写盘「新节点」→ 重建 → 自动进编辑框 → 输入 abc → 提交
  → previewText 改 DOM（卡片显示 abc）→ editSvc 写盘 → refresh 判 patch
  → applyPatch 只换 innerHTML（已是 abc，changed=false）→ payload.src 仍说「新节点」
  → 再点编辑：value = 「新节点」；失焦提交时 value === src.text 判 none → 不写盘
  → 卡片退回 DOM 的 abc。症状完全对上。
```

修：`Projection.patch` 带上**新树**里那个节点的 `src`（`plan.ts`），
`applyPatch` 换引用（不是 Object.assign —— 新行可能少了 endLine/blockStart，
逐字段覆盖会把旧值留下来让 startEdit 误判多行）。日志 `patch.src from->to` / `patch.src.miss`。

### Bug 2（1.18.4 新引入，飘线的直接原因）：补孩子用的是错的 path 拼法

`paintMoved` 里「父动了，子必须重画」用 `this.index.get(\`${path}.${i}\`)`。
但 markmap 的 `state.path` 由 `state.id` 拼成，**不是下标**（现场：父 `1.6`，子 `1.6.8`）。
于是一条都没命中，补孩子是**死代码** —— 1.18.4 声称修了飘线，其实没生效。

修：遍历 `data.children`，读孩子自己的 `state.path` 去 index 里取。

验证（`tmp/driftProbe.ts` 加了三段）：
```

父单独右移 40px  max=40.0  worst=甲1 40.0,甲2 40.0
paintMoved(父)  max=0.0        ← 修复前这里是 40.0
```

### 顺带
- `obs.structural` 分支：结构变化那一批里同时有 transform 变化时，先同步
  `paintMoved(moved)` 再 `requestAll()`（原来只等下一帧全量 = 有一帧「卡片到位、线没到」）。
- 日志：`link.drift {n,max,skip,frozen,worst}`（每帧自检线的 d 与按当前几何重算的差；
  `painter.measureDrift`，只排一次 rAF、200ms 限流、只在 tracing 时跑）、
  `patch.src`、`drag.pick`（整块成员数 vs 总数）、`drag.drop {rebuild}`、
  `drag.shift.gone/timeout`、`paint.moved` 加 `miss`（索引里找不到的孩子）与 `nogeo`。
- 测试 T24：patch 必须带出新 src（`src.text` 是新文字、line 指向被改行、none 不退化）。

## 1.18.7：「拖动带线」的真正原因 —— 藏线是一次性动作，而重绘会把线接回去

日志 `112810.log`（253 节点）时间线：
```
 9635.8 drag.pick members=3 roots=1
 9713.3 drag.links n=1            ← 摘掉块根的对外线
 9879.7 obs.structural recs=13 child=6   ← 提层的 appendChild（每个 g 两条记录）
 9883.1 paint.all boxes=257       ← 拖动中途一次全量重绘
11662.7 drag.drop rebuild=true    ← 这之间 1845ms 全程带线
```
机制：`painter.applyLink` 开头有「凡我画过的线都保证可见」（防 d3 复用元素后线永久消失），
于是**任何一次重绘都会把 display 抹掉**。拖动开始时 `beginDrag` 的 `parent.appendChild`
（提层，防目标卡片遮挡）产生 childList → 观察器判成结构变化 → 全图重绘 → 线回来了。
「有线」和「拖动带线」是同一个根因。

更糟的一种：块根在按下时**还没有**那根 path（`ensureLayers` 还没跑、或元素被复用换过），
摘不到 → 任何重绘都会补出一根，而 `linkPath` 只读 `transform` 属性、**不含 CSS translate**
→ 那根线按旧位置算完再跟着 g 平移，就是一根浮在空中的线。

### 改法（三条，缺一不可）
1. **藏线变成谓词**：`NodePainter.shiftedRoots: Set<SVGGElement>` + `markShifted(els, on)`；
   `applyLink` 命中就只保证 `display:none`（不写 d、不动缓存）后 return。
   删掉了原来「摘掉 → 重建时记得还」的语义 —— 判据消失后下一次绘制自然恢复（fail-open），
   失败方向从「线永久消失」变成「最坏早一帧露线」。覆盖了所有重绘入口
   （paintAll / paintMoved 的父动补画 / reflowNow / settle 钩子），也覆盖「新补出来的 path」。
2. **提层的 childList 记录必须吞掉**：`MindmapView.raiseNodes()` =
   `takeRecords()`（先把积压交给 `handleMutations`，丢掉会让线停在旧位置）→ `disconnect()`
   → `appendChild` → `observe()`。不要用「按 class 猜哪条是我干的」：每个 appendChild 产生
   **两条**记录（add=0/rem=1 与 add=1/rem=0，实测），而且回调可能被主线程拖后 166ms，
   那时 class 早被摘掉了。探针实测：吞掉后拖动期间 childList 记录 = 0（不吞 = 6）。
3. **重建收尾只清「不是手上这一块」的**：`sweepDragShift(skip)` + `painter.reset()` 之后
   重新 `markShifted(liveRoots)`。否则用户放手后立刻抓下一个节点、上一次的重建正好收尾时，
   会把手上这块当场拽回原处（`drag.liveMembers()/liveRoots()` 提供判据）。

### 验证（`tmp/dragProbe.ts` 扩了三个断言）
```
拖拽中·强制重绘后  links=1 visible=0        ← 重绘不再把线接回来
提层产生的 childList 记录 0
松手(不重建)       outerRestored=true      ← 判据消失后线自己回来
无对外线·重绘后    before=1 visibleAfter=0  ← 新补出来的 path 也不会露出来
```
`measureDrift` 里改为把 shifted 的线单独计 `shifted++`，不算 `hidden`（否则拖动时
「线不见了」的唯一告警一直在响）。

## 1.18.8：重绘的证据链与「写入量」这个指标

用户问「重绘的最佳实践」，四个子 agent 并行调研（浏览器渲染 / d3 join / 图形编辑器架构 /
本仓库审计），交叉验证后改了三处。

### 调研里最要紧的四条
1. **`getBBox` / `getComputedStyle` / `getBoundingClientRect` 才强制同步布局，`getAttribute`
   不会。** 本仓库 `paintAll` 内部这三样一次都没有 —— 设计是对的，所以成本不在「读」，
   而在**写**：每次写属性都让那张卡片的排版作废，整图 style/layout 重算一次。
2. **`<g>` 不是图层。** 想缩小失效面积只能靠独立容器；SVG 没有开发者可控的 dirty-rect。
   所以「分层」对本项目的收益是架构性的（z 序、独立缓存），不是性能。
3. **d3 的 `join()` 只保证「key 命中就复用元素」，不保证清理状态。** markmap 的 key 含
   全局 DFS 序号，中途插删节点会让整条尾巴换 key → 全量 enter/exit。这是上游限制，
   改不动；能做的只是「`setData` 之后不要全量重画」。
4. **d3 官方对「只改一个节点」的答案就是 keyed join + 只写变化的属性**；`transition().duration(0)`
   不是同步写 —— 首次 tick 被推迟到帧末（`schedule.js:101`），这才是「设了 0 还闪」的机制。

### 改法（都是「少写」，不是「少画」）
- `NodePainter.reset()` **保留 `entries`**，只清 `index`/`shiftedRoots`。d3 按 key 复用 g，
  一刀切清缓存等于强制下一次全量重写。单条失效靠 `entryOf` 的身份核对。
- 新增 `writes` 计数器 → 日志 `paint.all writes= fresh=`。**writes 才是成本**。
- `isContentChurn()`：`foreignObject` 内部的 childList 判成「文字重渲染」，不是结构变化
  → 改一个字不再额外排一次全量。
- `paintMoved` 对尺寸变了的节点也补 `applySize/applyCircle`（旧版只在 `!entry.link` 时补）。
- `paintSelection` 用 `(structureGen, 选中集合)` 做键早退；`prune` 去掉「数量相等」短路。

### 实测（`tmp/paintProbe.ts`，197 节点）
```
A 冷启动           writes=4954  ms=9      ← 基线：每节点 24 个属性
B 原样重画         writes=0     ms=2      PASS
C setData 改一字    writes=25    ms=2      复用 g=196/197   PASS
D 改内容变宽        writes=43    ms=1      卡片 400 / 文字层 368  PASS
E 再画一遍         writes=0               PASS
```
旧版 C 与 B 都会是 4954。改一次字从「两次全量 ≈ 1 万次写」降到 25 次。
`dragProbe` 全部断言（提层记录 0 / 强制重绘 links=1 visible=0 / 重建收尾 swept=6）仍通过；
`tsc` 干净、`npm test` ALL PASS、`smoke` 通过，1.18.8 已部署（sha1 `f26392cf…`）。

### 还没做的（评估过，收益/风险不划算或需要用户定）
- 视口裁剪（culling）：React Flow 维护者自己承认 `onlyRenderVisibleElements` 反而更慢
  （重新进视口要昂贵重建）；250~1000 节点不该做。
- 折叠只画受影响子树：markmap 会让尾巴换 key 全量 enter/exit，局部化没有语义基础。

## 1.18.10：编辑完成「文字顶出卡片边框」——卡片一次都没被重画

截图现场：刚改完的那张卡片，新文字明显比卡片宽，右边直接溢出边框，而且不会自己恢复。

### 证据链（代码级，不是猜）
1. `previewText`（提交即预览）把新 innerHTML 铺上卡片，量 `box.scrollWidth` 写进
   `fo.width/height`，然后 `reflowSoon()`。
2. 那个 rAF 到点时 phase 还是 `editing`（`runWrite` 还在 await），而 `reflowNow` 的闸门
   是 `phase !== "idle"` → 直接 `reflow.skip` 返回，**一次画都没画**。
3. 写盘完 `refresh()` → `applyPatch`：innerHTML 已被预览铺成一样 → `changed=false`
   → 不请求重排（只又写了一次 fo.width）。
4. markmap 100ms 后自己的 `renderData`：把 fo.width 写成正确值、class 全量重写，
   但这个节点**只是往右变宽、坐标没动** → transform 全是同值 → 被观察器同值过滤掉；
   `class` 通道只补选中框（`paintSelectionOn`）。**没有任何一次绘制。**

所以不是「画错了」，是「一次都没画」。`fo.width` 是文字层，我们的卡片是另一个 `<rect>`，
属性变了不会自己变大。

### 改法
1. **观察器加 `width`/`height` 通道**（`attributeFilter` + `oldValue` 比值），命中就
   `paintMoved` 那一批（日志 `obs.resize n=`）。成本：markmap 每次 renderData 写一次，
   同值直接丢；折叠动画只写 transform，不会每帧触发。
2. **写完 `fo.width/height` 当场 `frames.paintMoved([g])`**（`previewText`、`applyPatch`、
   以及预览失败回滚），不再把重画托付给 `reflowNow`。
3. **`reflowNow` 的闸门从 `!== "idle"` 放宽到 `=== "rebuilding"`**（与 `blocked()` 一致）。
   编辑态的 DOM 是完整的（编辑框是浮层，原文只是 visibility: hidden），没理由不让它重排。
   顺带修掉「编辑期间 markmap 自己那次重排没被压住」的老问题。
4. TS 会把握手处的窄化带到 `await` 之后（第二处 `=== "rebuilding"` 报「类型没有重叠」）
   → 抽出 `private rebuilding()` 方法。
